# 设计决策记录

## 零运行时依赖

**决策：**只使用 Node 内置模块和浏览器原生 JavaScript/CSS。

**原因：**

- 启动简单；
- 减少 npm 供应链风险；
- 复制目录后只要有 Node 和 Git 即可运行；
- Windows 用户不需要额外安装。

**后果：**编辑器和 UI 需要自行实现，优先调用成熟的 Git 命令，不重新实现 Git 语义。

## 服务端拆分为原生 CommonJS 模块

**决策：** `server.js` 拆成薄入口 + `src/` 下 13 个模块，仍用 `require`，不引入构建步骤。

**原因：**

- 单文件 1999 行的边际成本已经偏高，AI 迭代每次都要读全文；
- 浏览器侧暂未拆分，先把影响面小、有测试覆盖的服务端拆掉；
- 原生 CommonJS 不需要打包器，复制目录即可运行，零依赖不变。

**后果：** 模块边界由 `@module` 头注释和 `docs/MAP.md` 共同维护；新增动作在 `src/git-actions.js` 的 switch 登记；新增顶级路由在 `src/routes.js` 登记。

## 数据模型 v3：显式 order 字段

**决策：** 仓库元数据增加 `order` 字段，工作区内从 0 连续；`loadState()` 按 `(workspaceIndex, order)` 排序顶层 `repositories` 数组。

**原因：** v2 用顶层数组相对顺序表达排序，增删/移动时只能用"ids 完整覆盖"兜底，易错位且难以局部更新。

**后果：** `reorderRepositories` 只更新 `order`，不再重排数组；`addRepository`/`moveRepositoryToWorkspace`/`deleteWorkspace` 都维护 `order`；迁移可重复执行，已存在合法 `order` 时只做密集化。

## 桌面壳 A：HTTP 内核 + --app 窗口

**决策：** 在零依赖前提下，用系统自带的 Chrome/Edge `--app` 模式包一层独立窗口，而不是 Electron/Tauri。

**原因：**

- 用户明确要求做成桌面应用且坚持零依赖；
- Node 无 GUI 能力，窗口只能借用系统浏览器；
- `--app` 模式无地址栏、无标签页，形态接近桌面应用；
- 单实例 + 心跳看门狗解决"多开"和"关窗后服务残留"。

**后果：** 任务栏图标仍是 Chrome/Edge（PWA 安装可后续替换）；`start.cmd` 通过 PowerShell 隐藏控制台启动；`GITDECK_DESKTOP=1` 启用固定端口、单实例、心跳退出。原"使用本地 HTTP 服务而不是原生桌面外壳"的决策被本决策扩展，HTTP 内核不变。

## 使用本地 HTTP 服务，而不是原生桌面外壳

**决策：**Node 本地服务 + 浏览器 UI。

**原因：**

- 不依赖 Electron/WebView2 打包；
- 易于迭代和截图验证；
- 跨浏览器可用。

**后果：**目录选择、下拉框、弹窗和无障碍交互都要由 Web UI 实现。

## 使用内置目录选择器

**决策：**用 `/api/directories/list` 和自定义目录浏览器替代 Windows `FolderBrowserDialog`。

**原因：**后台服务启动的原生对话框可能不可见或被阻塞，导致请求一直等待。

**后果：**盘符和路径导航由应用自己维护。

## 精确设置 `safe.directory`

**决策：**每次 Git 操作只传入当前精确仓库路径。

**原因：**Windows 本地开发中仓库所有者和运行账号不一致很常见。

**后果：**仓库仍然必须由用户明确添加后才能操作。

## 关闭可选索引锁

**决策：**所有 Git 子进程默认设置 `GIT_OPTIONAL_LOCKS=0`，还原操作也显式设置。

**原因：**状态读取和还原不应该因为可选索引刷新而失败。

**后果：**add/commit 等真正修改索引的操作仍需要正常锁和写权限。

## 仓库只属于一个工作区

**决策：**每个仓库元数据只有一个 `workspaceId`。

**原因：**模型简单，迁移成本低。

**后果：**跨工作区操作是移动，不是复制。当前不支持同一仓库同时属于多个工作区。

## 移除不等于删除目录

**决策：**删除工作区、移除仓库和批量移除只修改 `data/repositories.json`。

**原因：**GitDeck 是管理工具，不是文件清理工具。

**后果：**物理目录需要用户通过资源管理器或终端删除。

## 选中提交使用 `git commit --only`

**决策：**暂存选中文件后使用 `git commit --only`。

**原因：**普通提交会把其他已暂存文件一起提交。

**后果：**“提交选中”和“提交全部已暂存”是两种明确不同的操作。

## 分支选择跟随搜索结果

**决策：**搜索条件变化时清空选择，“全选可删”只作用于当前筛选结果。

**原因：**避免误删被搜索条件隐藏的分支。

## 三个自定义分隔条

**决策：**使用 CSS 变量和 Pointer Events 实现拖动，不引入布局库。

**原因：**无依赖且实现直接。

**后果：**响应式规则需要在媒体查询中持续维护。

## 工作区使用自定义下拉菜单

**决策：**不用原生 `<select>`，改用与仓库右键菜单一致的菜单。

**原因：**原生下拉样式不一致，辨识度低。

**后果：**需要在 `app.js` 中维护点击外部关闭、Escape 和键盘可访问性。
